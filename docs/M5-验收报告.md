# M5 验收报告：帧同步（Barker-13）+ 相位模糊求解 + 载荷提取

日期：2026-10-04  接收链标记：spxh-m5  版本：0.1.0

## 1. 范围与交付物

M5 把 M3 的符号流、M4 的译码结果接到**帧结构**上，走完"从 I/Q 到可读业务比特"的最后一步：

    spxh/core/framesync/
      preamble.py   Barker-13 期望符号/比特模板 + 归一化滑动相关（符号域与比特域）
      extract.py    解调 -> 前导同步（含相位模糊求解）-> 帧头解析 -> CRC -> 载荷 -> 真值对账
    scripts/check_m5.py   验收自检（同步率 / 相位模糊 / 低信噪比 CRC 失败率 + 出图）

配套：CLI 新增 spxh frame；HTTP 接口新增 /api/frame（契约第 12 节）；前端新增第 7 个标签页「帧」。
测试从 267 项增至 279 项。

## 2. 关键设计

### 2.1 用前导把相位模糊解掉（M3 的遗留问题在这里闭环）

M3 的判决导向载波环只能锁到星座的某个对称点（BPSK 180 度、QPSK 90 度、8PSK 45 度、
16QAM 90 度），因此 M3 的验收里只能"拿真值去搜旋转"来对账 —— 那是评估手段，不是接收机能力。

M5 用**已知前导**解决它：把 Barker-13 按当前调制映射成期望符号，与接收符号做归一化复数相关，
**相关峰的相位就是整段星座的旋转角**；把它旋回去，模糊就解掉了。M5-B 的实验直接验证了这一点
（人为把整段信号旋转，M5 不看真值也能自己纠正）：

| 调制 | 注入旋转 | M5 解出 | 帧数 | CRC 通过 |
|---|---|---|---|---|
| BPSK | 180 度 | 180 度 | 8 | 8 |
| QPSK | 90 / 180 / 270 度 | 90 / -180 / -90 度 | 8 | 8 |
| 16QAM | 90 / 180 / 270 度 | -180 / -90 / 0 度 | 4 | 4 |

（解出的角度与注入角度在"模对称阶数"意义下相等，例如注入 270 度、解出 -90 度。）

### 2.2 为什么不能"取相关峰最大者"就完事

Barker-13 的低旁瓣是针对**它自己的非周期自相关**说的。当它埋进**随机载荷**里时，
随机数据在某个错位处凑出 0.9 以上的归一化相关是常事 —— 实测 BPSK 20 dB 下最大峰落在载荷深处，
解析出 0xfc 这种非法 MAGIC。因此 M5 做的是"**相关出候选 + 逐候选试解析**"：

1. 相关序列取前 12 个候选峰（按幅值排序 + 间隔抑制，避免同一主瓣重复计数）；
2. 每个候选给出起点，并把该调制的**全部对称旋转**都试一遍；
3. 按帧结构连续解析，统计"成功帧数 / CRC 通过数"，取得分最高者。

这既压掉虚警，又顺手把相位模糊定下来 —— 就是接收机里"用已知序列验证假设"的标准做法。

### 2.3 一帧坏掉不能丢掉后面所有帧

解析失败时按"预期帧长"跳过继续；CRC 不通过的帧**照样记录**（前导/帧头/CRC 三段状态分别标出），
只有连前导和帧头都读不出来才计为失败。原始实现里一帧 CRC 失败就 break，等于把 8 帧的结果
缩成 2 帧 —— 这种"看起来更严格、实际是丢数据"的行为已经改掉。

## 3. 验收结果

### 3.1 帧同步与载荷提取（注入 0.35 符号定时偏移 + 37 Hz 频偏，同步**不用真值**）

8 帧 x 64 字节载荷；下表为 30 dB（判据点）：

| 调制 | 相关峰 | 解析帧数 | CRC 通过 | 载荷字节 | 与真值逐字节一致 | 判定 |
|---|---|---|---|---|---|---|
| BPSK | 0.957 | 8 | 8 | 512 | 512 | PASS |
| QPSK | 0.957 | 8 | 8 | 512 | 512 | PASS |
| 8PSK | 0.999 | 7 | 7 | 448 | 448 | 见局限 |
| 16QAM | 0.979 | 7 | 7 | 448 | 448 | PASS |
| 2FSK | 1.000 | 8 | 7 | 512 | 448 | PASS |
| 4FSK | 1.000 | 8 | 7 | 512 | 448 | PASS |

* 15~30 dB 全表都跑过：BPSK/QPSK 从 15 dB 起就是 8/8 全对；8PSK/16QAM 从 20 dB 起 7/7。
* **记录首尾各损失约 1 个符号**（定时环从滤波器峰值附近起步、到记录末尾停止），
  因此 4 帧的记录里最高阶调制常常少 1 帧 —— 把记录加长到 8 帧后，这一帧的损失占比从 25% 降到 12%。
* 2FSK/4FSK 恒定有 1 帧 CRC 不过：FSK 是非相干检测、M3 里**没有定时环**，
  0.35 符号的采样相位偏差会让相邻音调的相关窗骑到边界上。M5 为此加了**采样相位搜索**
  （用分数延迟滤波器按 ±1/±2/±2.5/±3 采样重解调，取解析得分最高者），
  无偏移时可做到 8/8，有 0.35 符号偏移时仍剩 1 帧 —— 如实记录在已知局限里。

### 3.2 低信噪比下的 CRC 失败率（无编码链路）

| 调制 | 5 dB | 10 dB | 15 dB |
|---|---|---|---|
| BPSK | 100% | 0% | 0% |
| QPSK | 100% | 67% | 0% |
| 2FSK | 100% | 67% | 25% |

这正是 M4 编码链存在的理由：不加纠错，10 dB 左右一帧就会错几个比特，CRC 直接判死。
把 M4 的 Viterbi/RS 接进这条链（M5 之后的工作）就能把 CRC 通过率拉回来 ——
而 M3 已经把 LLR 标定好了，M4 的软判决接口现成。

## 4. M5 期间发现并修复的问题

1. **前导 ±1 约定与星座反了**：一开始按"比特 1 -> +1"写模板，而 M0 的 BPSK 星座是
   "比特 0 -> +1、比特 1 -> -1"，结果比特域相关的峰值整体反号（正相关峰变成 -1、
   相位模糊会判反 180 度）。改正后峰值 +1、反相前导 -1，据此判模糊。
2. **取全局最大相关峰 = 大量虚警**：随机载荷能凑出 0.99 的相关。改成"候选 + 试解析 + 打分"。
3. **一帧 CRC 失败就 break**：把 8 帧结果缩成 2 帧。改成按预期帧长跳过并继续，失败帧如实记录。
4. **短前导（16QAM 只有 3 个符号）下相位不可靠**：只信相关峰相位会选错旋转。
   改成对每个候选遍历全部对称旋转，用"前导 + 帧头 + CRC"的真实解析结果来选。
5. **FSK 没有定时环**：0.3 个符号的边界偏差就让相邻音调相关窗骑界，恒定 1 帧 CRC 不过。
   加了采样相位搜索（先用"补零"实现，反而把最后一帧尾巴切掉，换成分数延迟滤波器才对）。
6. **前端"帧"页只画了 HTML 没接数据**：并行子代理只完成了 index.html 的标签与面板就停了；
   这里补齐了 app.js 的 TABS/状态/加载/渲染/画布/事件与 CSS、mock。
7. **setText 的调用约定搞错（我的错）**：本项目里 setText(id, text) 的第一个参数是**元素缓存的键名**
   （内部再做 el[id]），我却按"传 DOM 节点"写，导致同步条与计数全部停在占位符 —— 而且它**不报错**，
   静默失效。是并行子代理在复核时逐处抓出来的（13 处），已全部改为键名写法。
   教训：这类"静默无害失败"必须靠静态审计兜住 —— 现在有一条检查：所有 setText('X') 的键
   必须在 cacheEls 的 el.X = $(...) 里出现（当前 34 个键全部命中）。
8. **"峰值/最大旁瓣"这个指标在本场景不成立**：Barker 的低旁瓣只针对它自己的非周期自相关，
   埋在随机载荷里时别处凑出的相关值经常超过真峰（实测 QPSK 给出 -0.17 dB 这种负数，
   子代理也质疑了这一点）。改成"峰值 / 全序列中位数的 dB 比"（峰显著性，必然 >= 0），
   并在 evidence 里补 peak_percentile 作为佐证；契约第 12 节同步更正了口径与 locked 判据
   （locked = 相关峰 >= 0.25 且至少解析出 1 帧 —— 相关峰再高、一帧都解析不出来仍算未锁定）。

## 5. 已知局限

- **记录首尾各损失约 1 个符号**：定时环的起止位置决定了首尾各少一个符号；帧数少时
  （4 帧）会表现为"少一帧"或"最后一帧 CRC 不过"。判据里对 FSK 允许少 1 帧，8 帧记录下不影响结论。
- **8PSK 在 15 dB 及以下同步不稳**：继承 M3 的 8PSK 误码地板（EVM 约 25%），
  13 位前导都读不全。20 dB 以上正常（7/7）。
- **FSK 的 1 帧损失**：见 3.1，采样相位搜索能弥补大部分但不是全部。
- **编码链尚未接进帧结构**：M4 的 Viterbi/RS/LDPC 已独立验收，但 SynthConfig(fec=...) 仍显式
  抛 NotImplementedError；把编码接进合成器与 M5 的载荷提取是本阶段之后的第一件事。

## 6. 快速使用

    # 命令行：帧同步 + 载荷提取（有真值自动逐字节对账）
    python -m spxh frame data/demo/qpsk_snr+10.0_000.sigmf-meta

    # 验收自检
    python scripts/check_m5.py

    # 前端「帧」页：同步状态、相位模糊表盘、相关峰、帧表、载荷 HEX/ASCII
    python -m spxh serve      # http://127.0.0.1:8760/ ，切到"帧"标签

    # 离线看效果（不依赖后端）
    http://127.0.0.1:8760/?mock=1&tab=frame

Python API：

    from spxh.core.io import load_signal
    from spxh.core.framesync import extract_frames

    signal = load_signal("data/demo/qpsk_snr+30.0_000.sigmf-meta")
    result = extract_frames(signal, modulation="qpsk")
    print(result.ambiguity_rotation_deg, result.summary)
    for frame in result.frames:
        print(frame["crc"]["ok"], frame["payload"]["ascii"][:40])
