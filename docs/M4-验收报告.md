# M4 验收报告：解交织 + Viterbi + Reed-Solomon + CCSDS 级联 + LDPC

日期：2026-10-04  编码库标记：spxh-fec  版本：0.1.0

## 1. 范围与交付物

M4 补齐"从解调软信息到可用比特"的最后一层保护，四个编解码器全部可用、可测、可解释：

    spxh/core/fec/
      interleave.py      矩阵块交织、卷积交织（含冲刷段）与精确逆运算、符号交织
      viterbi.py         卷积码 K=7 r=1/2 (133,171)8；硬判决（Hamming）与软判决（LLR）Viterbi
      reed_solomon.py    GF(256) 上的 RS(255,223) 及缩短码：BM + Chien + Forney，明确不可纠标志
      ccsds.py           级联链：RS(255,223) x I + 符号交织 + 标准卷积码
      ldpc.py            Gallager 正则 (1152,578) + 对数域归一化最小和迭代译码
    scripts/check_m4.py  验收自检（BER/BLER 曲线、软判决增益、RS 纠错与交织价值、出图）

配套：CLI 新增 spxh fec；HTTP 接口新增 /api/fec（契约第 11 节）；前端新增第 6 个标签页"译码"。
测试从 245 项增至 267 项，全部通过。

## 2. 关键设计

### 2.1 为什么先有 M3 的 LLR，再有 M4 的软判决

软判决译码吃的是 LLR 的**尺度**：LLR 偏大（过度自信）会让 Viterbi 在错误路径上"死不认错"，
LLR 偏小则等价于丢掉了可靠性信息。M3-C 已经用"期望误码数 vs 实测误码数"验证了 LLR 尺度可信
（5 dB 时比值 0.99），所以 M4 的软判决路径是**直接可用**的，而不是摆设。

### 2.2 交织的定位

交织本身不纠错，它把**突发**摊薄成多个码字内部的**随机错误**。因此验收里专门做了一个
"同一段 32 符号突发，交织 vs 不交织"的对照实验（见 3.3），而不是只报一个码率。

### 2.3 参数选择的诚实性

* LDPC 用 Gallager 正则构造 (n=1152, dv=3, dc=6)。该构造有一个**已知秩亏**：
  每个子块的行异或都是全 1 向量，于是 dv 个子块间有 dv-1 个线性相关。
  实测秩 = 574（比标称 576 少 2），因此真实 k = 578、码率 0.5017。
  这里不假装是 0.5，也不偷偷补行：显式做秩判定、丢掉相关行，并把真实维度报出来。
* CCSDS 链保留级联结构与标准卷积码（这是决定编码增益量级的部分），
  但**没有**实现对偶基/随机化等互操作细节。因此它给出正确的增益量与正确的软判决接口，
  但不是"逐比特可互操作"的 CCSDS 实现 —— 这一点在报告与代码注释里都写明。

## 3. 验收结果

### 3.1 BER vs Eb/N0（BPSK + AWGN，按**信息比特**统计）

信道用 BPSK + AWGN 是刻意的：这样量到的是**纯编码增益**，不被同步/估计误差污染；
而 M3 的输出 LLR 可以直接接同一条链。

| 1 dB | 5.76e-2 | 2.34e-1 | 4.03e-2 | 5.67e-2 | 2.41e-2 | 6.22e-2 |
| 2 dB | 3.74e-2 | 1.17e-1 | 7.25e-3 | 4.15e-2 | 1.63e-3 | 1.95e-3 |
| 3 dB | 2.29e-2 | 2.75e-2 | 7.5e-5 * | 2.80e-2 | 4.2e-5 * | 1.3e-4 * |
| 4 dB | 1.24e-2 | 7.13e-3 | 7.5e-5 * | 1.69e-2 | 4.2e-5 * | 1.3e-4 * |
| 5 dB | 5.93e-3 | 5.50e-4 | 7.5e-5 * | 4.62e-3 | 4.2e-5 * | 1.3e-4 * |
| 6 dB | 2.35e-3 | 7.5e-5 * | 7.5e-5 * | 5.61e-4 | 4.2e-5 * | 1.3e-4 * |

说明：
* 带 * 的点是**实测零误码**。对数坐标画不了 0，因此报告里用 95% 置信上界 3/N 表示
  （例如 40 个码字 x 1000 比特 -> 7.5e-5），同时在 detail[].bit_errors 里给出真实误码数
  （0 即零误码），判据一律用 bit_errors 而不是这个上界 —— 不拿"上界"当"实测值"。
* 自校验：无编码曲线在 0 dB 处 7.91e-2，理论 Q(sqrt(2)) = 7.86e-2 —— 仿真链路本身是对的。
* 每个点跑了 40 个码字（卷积/LDPC）、16 个（RS）、8 个（CCSDS），信息比特量 3 万~40 万不等。
* 从 6 dB 起各编码都进入零误码区，表格里的上界随码字数不同而不同（N 越大上界越低）。

### 3.2 软判决增益（M3 认真标定 LLR 的回报）

| 参考 BER | Viterbi 硬判决 | Viterbi 软判决 | 增益 |
|---|---|---|---|
| 1e-4 | 5.86 dB | 2.94 dB | **2.92 dB** |
| 1e-3 | 4.77 dB | 2.43 dB | **2.33 dB** |

教科书对 K=7、r=1/2 卷积码的软判决增益约 2 dB。两次独立运行的实测：
1e-4 处 2.90 / 2.92 dB，1e-3 处 2.33 / 2.68 dB —— 都在 2 dB 量级，判据（>= 1.5 dB）稳定通过。
略高于教科书值且有一定波动的原因很明确：这是短块（1000 信息比特 + 6 尾比特）、瀑布区很陡，
交叉点对统计量敏感；把参考点从 1e-4 挪到 1e-3 就能看到这个敏感性（上表两行差 0.6 dB）。

真正要报告的是：**M3 标定的 LLR 尺度可以直接支撑软判决译码，不需要任何额外校准**。

### 3.3 Reed-Solomon 与交织的价值

* RS(255,223)，t = 16：随机注入 1 / 8 / 16 个符号错误全部纠正，恢复原始信息；
  注入 17 个符号错误时**明确报告不可纠**（用"纠正后伴随式必须全零"做硬判据，绝不静默错纠）。
* 缩短码 RS(100,68) 同样工作（纠正 8 个符号错误）。
* 交织对照实验（同一段 32 符号突发）：

| 处理 | 结果 |
|---|---|
| 不交织 | 32 个连续错误全落在一个码字上（> t=16）-> **不可纠** |
| 深度 5 符号交织 | 摊到 5 个码字，每个最多 **7** 个错（< t=16）-> **全部纠正** |

这就是交织器存在的意义，也是 CCSDS 选 I=5 的原因。

## 4. M4 期间发现并修复的问题

1. **Viterbi 的状态度量归并写错**：一个目标状态有两条前驱分支，用
   "new[target] = candidate"（fancy indexing 重复下标时最后一次赋值生效）会让**较差**的那条
   覆盖较好的那条。症状是**无噪声译码都译错**（输出恒为一串 1）。改为 np.maximum.at 后正确。
   这个 bug 很隐蔽：网格、生成多项式、回溯逻辑全都是对的，只有归并错了。
2. **RS 的 x^nsym 位移方向写反**：系数用"低位在前"表示时，乘 x^nsym 是**在高位补零**
   （前插），写成后补零会让余式完全错 —— 症状是"干净码字的伴随式不为零"。
3. **LDPC 的 Gallager 构造秩亏未处理**：H 的秩比行数少 2，直接做"后 M 列可逆"分块必然失败。
   改为显式秩判定 + 丢相关行 + 真实维度上报（k=578，码率 0.5017）。
4. **LDPC 迭代调度用错**：把"后验"直接当变量节点消息（后验里已含该校验节点自己的消息），
   消息互相污染 -> 各种信噪比都收敛不了。改为标准 flooding 调度 + 边映射（每条边有稳定槽位，
   更新时排除自身贡献）。
5. **丢行后列重不再均匀**：边映射假定列重恒为 dv，实际变成 2/3 混合。改为通用度分布映射，
   并把度分布记录进报告。
6. **卷积交织的冲刷长度算错**：输出长度不是 n + (depth-1)*step，而是
   n + step*depth*(depth-1)/2（depth=5, step=1 时多 10 个符号）。
7. **统计量不足导致曲线非单调**：LDPC 起初只跑 15 码字/点，3 dB 的点比 2 dB 还差
   （一个码字失败就占 BER 的很大比重）。加大到 40 码字/点后曲线恢复单调。
   教训：低误码率区间的点数必须够，否则报告里的"抖动"其实是统计噪声。

## 5. 已知局限

- **LDPC 不是标准码**：Gallager 正则短码 + 归一化最小和，4 dB 时 BER 约 1e-4、5 dB 到零误码；
  与 DVB-S2 / 5G NR 的基图（大码长、准循环、速率匹配）相比有差距。基图只是不同的 H，
  可按同一接口接入，但速率匹配、缩短/打孔、准循环结构尚未实现。
- **CCSDS 互操作性**：未实现对偶基、伪随机化、以及 CCSDS 具体交织器实现，因此不能与真实
  CCSDS 设备互通；级联结构与增益量级是正确的。
- **RS 单独使用时性能差**（无内码保护），这是符号级纠错的正常表现，级联后才体现价值。
- **未做差错/擦除联合译码**：RS 的擦除（erasure）译码可以把纠错能力翻倍，
  在帧同步能给出"可疑符号位置"时很有用 —— 留给 M5（帧同步）之后。
- **未做迭代（Turbo 式）级联**：CCSDS 链目前是"卷积译码 -> RS 译码"的一次性级联，
  没有把 RS 的软输出反馈回内码。

## 6. 快速使用

    # 查看编码目录与译码报告（前端"译码"页同源数据）
    python -m spxh fec

    # 重新跑验收（约 3~5 分钟，落盘 models/check_m4_report.json 与 docs/figures/m4_ber_curves.png）
    python scripts/check_m4.py

    # 前端"译码"页：编码目录、BER 曲线、软判决增益、验收清单
    python -m spxh serve      # http://127.0.0.1:8760/ ，切到"译码"标签

Python API：

    from spxh.core.fec import ConvolutionalCode, ReedSolomon, CCSDSCode, LDPCCode

    conv = ConvolutionalCode()                  # K=7, r=1/2
    coded = conv.encode(info_bits)
    decoded = conv.decode_soft(llr)             # 直接吃 M3 的 LLR（正数=比特 0）

    rs = ReedSolomon()                          # RS(255,223), t=16
    codeword = rs.encode(info_bytes)
    fixed, corrected, uncorrectable = rs.decode(received_bytes)

    ldpc = LDPCCode()                           # (1152, 578)
    result = ldpc.decode(llr)                   # 迭代译码，返回 converged/iterations

## 7. 下一步（M5）

1. 用 Barker-13 前导做帧同步，解决 M3 遗留的**相位模糊**（不再靠"旋转搜索"对账）。
2. 载荷提取：帧头解析（32 位）、CRC-16 校验、参数回填；把 M0 的帧结构真正打通。
3. RS 擦除译码：帧同步给出的可疑位置用于擦除，纠错能力翻倍。
4. 把 FEC 接进合成器（M0）与接收链（M3），做**端到端**（编码 -> 调制 -> 解调 -> 译码 -> 帧校验）
   的联合验收，而不只是本次的编码级链路仿真。
