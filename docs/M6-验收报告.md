# M6 验收报告：编码链接入帧结构（端到端）

日期：2026-10-04  链路标记：spxh-m6  版本：0.1.0

## 1. 范围

把 M4 的四种编译码器真正接进 M0 的帧结构、由 M3/M5 的接收链吃下来，形成完整闭环：

    载荷 -> 编码/交织 -> 成帧 -> 调制 -> (信道) -> 解调(M3) -> 帧同步(M5)
         -> 解交织 -> 软判决译码(M4, 直接吃 M3 的 LLR) -> 帧头解析 -> CRC -> 载荷

新增/改动：

    spxh/core/fec/codec.py        统一编码接口（长度计算、编码、译码、交织单位）
    spxh/core/framing/format.py   帧长/成帧/解析支持编码与交织；帧头 fec 字段扩到 3 bit
    spxh/core/synth/generator.py  SynthConfig(fec=..., interleave=...) 真正生效
    spxh/core/framesync/extract.py 旋转后重算 LLR，交给软判决译码器
    scripts/check_m6.py           端到端验收 + 出图
    CLI: spxh generate --fec/--interleave

## 2. 帧布局（M7 起更新：CRC 进编码）

    fec = none : Barker-13 + 帧头(32b) + 信息字节 + CRC-16（都不编码，与 M0 完全一致）
    fec != none: Barker-13 + 帧头(32b, 未编码) + 编码( 信息字节 || CRC-16 )

* 前导必须留在编码之外：帧同步要在译码**之前**做（编码会把已知序列打散）。
* 帧头留在编码之外：接收端必须先知道"用哪种码、交织没交织、多长"才能译码。
* CRC 覆盖**帧头 + 信息字节**（不是编码后的比特）：先译码、再校验，CRC 才真正说明
  "解出来的载荷是对的"。

**M7 第一步已经修掉的问题**：原布局里 CRC 字段自己是未编码的，低信噪比下"载荷逐字节完全正确、
却因为 CRC 被打错而判失败"（M6 首轮实测 8 dB 时约 15%）。现在把 **CRC 放进编码里**：
校验字段受同样的码保护，"CRC 通过"才真正等价于"整帧内容正确"。实测收益很直接 ——
卷积软判决的可用门限从 11.4 dB 降到 **7.8 dB**、LDPC 从 9.8 降到 **7.8 dB**。
帧头仍在编码之外（接收端必须先知道码参数才能译码），它的保护靠"CRC 覆盖帧头"间接保证。

## 3. 验收结果

### 3.1 端到端 CRC 通过率 / 载荷逐字节一致率（QPSK，注入 0.35 符号偏移 + 37 Hz 频偏）

| Es/N0 | 无编码 | 卷积(软) | RS(76,60) | CCSDS 级联 | LDPC(1152,578) |
|---|---|---|---|---|---|
| 6 dB | 0% | 0% | 0% | **100%** | 0% |
| 8 dB | 0% | 0% | 0% | **100%** | 0% |
| 10 dB | 0% | 67% | **100%** | **100%** | **100%** |
| 12 dB | **100%** | **100%** | **100%** | **100%** | **100%** |

### 3.2 可用门限（CRC 通过率 >= 90%）

| 方案 | 门限 (Es/N0) |
|---|---|
| 无编码 | 11.8 dB |
| 卷积(软) | **7.8 dB** |
| LDPC(1152,578) | **7.8 dB** |
| RS(76,60) | 9.8 dB |
| CCSDS 级联 | 9.6 dB |

**编码链把可用门限降低了 4.0 dB**（11.8 -> 7.8）。CRC 移进编码后，软判决译码器的真实能力才显出来：
卷积(软) 从 11.4 dB 改善到 7.8 dB、LDPC 从 9.8 到 7.8；无编码不变。

（需要诚实说明的两点：(1) 每个 Es/N0 点只跑 4 帧，CRC 通过率的量化步长是 25%，
"门限"是插值出来的、抖动不小 —— CCSDS 从上一版的 5.8 dB 变成 9.6 dB 主要就是这个原因，
它的自适应短码在本配置下是 RS(29,13)、保护并不强；给出平滑曲线需要每点跑更多帧。
(2) 卷积码没有内建错误检测，残余误码只能靠 CRC 兜，因此它的曲线在门限附近很陡。
纯编码增益的严格对比在 M4 的链路上做过：软判决相对硬判决 2.9 dB。）

## 4. M6 期间发现并修复的问题

1. **交织必须按"码的纠错单位"来打散（最重要的发现）**：一开始统一按**比特**做块交织，
   结果 RS 反而被打垮 —— 32 比特突发摊到 32 个字节里，每个字节错 1 比特就是 32 个**符号**错误，
   远超 t=8（实测 RS+比特交织 8 次全败，而不交织 8 次全成）。改成"卷积/LDPC 按比特、
   RS/CCSDS 按字节"之后，两端都对了。这也正好解释了 CCSDS 为什么规定**符号**交织。
2. **帧头 fec 字段不够用**：原来是 2 bit（none/conv/rs/ccsds），塞不下 LDPC。把原来的保留位
   并入 fec 字段（bit3-1），fec=none 时字节与旧布局完全一致，已有数据与测试不受影响。
3. **CCSDS 交织深度与任意长度**：CRC 进编码后信息多了 2 字节，60 字节的载荷在深度 5 的级联里
   不再整除。改成"在信息尾部补零到深度倍数"，任意载荷长度都能用，收发两端算法一致。
4. **候选峰预算太小**：编码帧更长、前导相对更短，弱信噪比下前 12 个候选峰可能全是虚警，
   真正的帧起点没被试到（实测 8 dB 的 CCSDS 案例 0 帧）。候选预算提到 40、阈值降到 0.35 倍后正常。
5. **垃圾帧头会让整次提取崩掉**：候选起点偏了就会把载荷当帧头读，payload_len/fec 变成随机值，
   帧长计算抛异常一路冒到顶。现在解析器把"帧头非法"当作**解析失败**返回，提取器也只接受
   "帧结构完整且长度自洽"的候选 —— 单个错误候选不能打断整帧提取。
4. **生成器不再拒绝 fec/interleave**：M0 时代的 NotImplementedError 换成参数自洽性检查
   （帧长必须能由 payload_len + fec + interleave 唯一确定），并更新了对应的旧测试。
5. **前端相关**：并行子代理修复了 13 处 setText 误用（本项目 setText 的第一个参数是元素缓存的
   **键名**，我却按 DOM 节点传，结果静默失效）；这里补了 favicon 路由与 mock 文件回退，
   消掉浏览器控制台里那条无害但扎眼的 404。

## 5. 已知局限

- **CRC/帧头未编码**（见第 2 节）：低信噪比下 CRC 字段自己会错。修法是把 CRC 移进编码，
  帧头仍留在外；这样"CRC 通过"才等价于"整帧内容正确"。
- **CCSDS 参数是自适应的缩短码**：为适配任意载荷长度，RS 用 (k+16, k)，交织深度固定 5；
  不是 CCSDS 标准互操作实现（对偶基/随机化未做）。
- **每点只跑 4 帧**：CRC 通过率的分母小，低信噪比区间抖动大；完整曲线需要更多帧与更长记录。
- **接收端不做"盲编码识别"**：目前由帧头告诉接收端用哪种码；若连帧头都不信，需要对
  5 种编码 x 交织开关做假设检验（架构上已经支持候选打分，只是没打开）。

## 6. 快速使用

    # 生成一个编码链路案例（CCSDS 级联，8 dB）
    python -m spxh generate --mod qpsk --snr 8 --fec ccsds --payload-len 60 --frames 6 \
        --out data/demo/qpsk_ccsds_snr+8.0_000

    # 命令行解出载荷（自动解交织 + 软判决译码 + CRC）
    python -m spxh frame data/demo/qpsk_ccsds_snr+8.0_000.sigmf-meta

    # 前端「帧」页直接看：帧头 fec=ccsds、CRC 通过情况、载荷 HEX/ASCII
    python -m spxh serve      # http://127.0.0.1:8760/

    # 端到端验收（约 2 分钟）
    python scripts/check_m6.py
