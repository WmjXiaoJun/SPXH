## 2. 帧头 CRC-8 与长度维盲恢复

帧头从 4 字节变 5 字节：第 5 字节 = 前 4 字节的 CRC-8（poly 0x07，标准向量 CRC8("123456789")=0xF4）。
代价是每帧 +8 比特；收益是：

1. **立刻发现帧头被打错**（1 字节开销挡住 255/256 的随机错误）；
2. **让"载荷长度也被打错"可恢复**：对 (编码, 交织, 长度) 的假设**重写帧头**、用 CRC-8 过滤、
   再用帧内 CRC-16 做终判。CRC-8 是很便宜的筛子，滤完只剩个位数假设需要真正译码。

实测（改坏长度字段的 3 个比特，五种编码）：

| 编码 | 按帧头声明解 | CRC-8 过滤后的候选 | 盲恢复结果 |
|---|---|---|---|
| none / conv / rs / ccsds / ldpc | 全部失败（预期） | 12 个以内 | **全部恢复，载荷逐字节一致** |

**端到端收益**（16 帧，注入 0.35 符号偏移 + 37 Hz 频偏；"盲恢复"= blind=1）：

| 编码 | 6 dB | 8 dB | 10 dB |
|---|---|---|---|
| 无编码 | 2 -> 2 | 7 -> 7 | 15 -> 15 |
| 卷积 | 2 -> **4**（CRC 1->4） | 5 -> **11**（CRC 5->11） | 13 -> 13 |
| CCSDS | 1 -> **4**（CRC 0->2） | 4 -> **12**（CRC 4->10） | 13 -> 13 |

为什么无编码不变、编码链路翻倍？因为**编码帧的载荷本来就能纠错**，卡住它们的是那个"没保护的帧头"；
帧头一坏，整帧就被丢掉。帧头 CRC + 盲恢复把这一类丢失救回来了。无编码帧没有冗余可救，
它失败的原因是载荷 CRC 不过 —— 盲恢复救不了（如实保留）。

工程代价与配套：
- 既有 demo 数据是 4 字节帧头生成的，**必须重建**（已重建 32 个案例），否则会整体误解析；
- /api/frame 新增 header.header_crc_ok / header_crc8 / crc8_expected 与 sync.blind.*；
- 帧头不可信时，序列推进改用**最近一次可信帧长**，不再被垃圾长度带跑偏。

## 3. "更强前导"的实测结论：瓶颈不在检测

实现并 A/B 了"更长检测模板"：13 位 Barker + MAGIC(8) + 调制码(4) = 25 比特
（QPSK 从 6 个符号涨到 12 个符号，积分长度翻倍）。同一信号、同一配置下对比：

| 检测模板 | 6 dB | 8 dB | 10 dB |
|---|---|---|---|
| 仅 Barker-13 | 2/16 | 7/16 | 15/16 |
| Barker + MAGIC + 调制码（25 bit） | 2/16 | 7/16 | 15/16 |

**完全相同**，而且在 16QAM 上还出现了相位歧义解析退化。结论：**5~8 dB 的召回瓶颈不是检测统计量，
而是"帧头没有保护"** —— 所以把这个改动回退了（不留没有实测收益的机制），
真正的收益来自第 2 节的帧头 CRC + 盲恢复。

进一步的证据（16QAM，注入 0.35 符号偏移）：30 dB 时原始比特流仍有 **2125 个比特错误**，
15 dB 是 2112 个 —— 与噪声无关的**地板**；8/8 帧的"前导+帧头"区间全被污染，
只有记录后段偶尔能解出帧（解出的帧逐字节正确）。这解释了为什么高信噪比下 16QAM 的
帧召回依然很低：定时环收敛瞬态 + M3 的 16QAM 误码地板把记录前段吃掉了。
据此把 16QAM 从 M5 的"必须通过"降级为 **known-limit**（与 8PSK 同类），
判据里写清实测依据，不靠放宽阈值掩盖。

## 4. LLM 怎么结合：报告层（narrator）

### 4.1 分工原则（这是关键，不是"把 I/Q 丢给模型"）

- **LLM 不做数值估计**。所有数字来自确定性管线（M1 估计 / M2 分类 / M5 帧同步 / M8 谱相关），
  每条证据都带 source / unit / confidence。模型只做**解释、整合、找矛盾、给下一步建议**。
- **结构化证据 -> 提示词 -> 结构化报告**。提示词是紧凑 JSON 证据表，硬性要求"只允许引用
  给定字段的数字，缺就写 null"；返回的报告结构与离线渲染**完全一致**。
- **离线确定性回退**。没有 key / 网络 / provider 时用同一份证据做确定性中文渲染，
  结构一模一样 —— 平台不能因为 key 失效就不可用。
- **可审计**。接口回传实际发出去的提示词（prompt_preview），报告里每条结论都挂 evidence。

### 4.2 实现

    spxh/core/report/narrator.py
      collect_evidence(path, ...)   跑管线收证据（纯数据，不生成文字）
      render_offline(evidence)      确定性中文报告（headline/sections/uncertainties/next_actions）
      build_prompt(evidence)        证据表 -> 提示词
      call_llm(prompt)              OpenAI 兼容 /chat/completions（只用标准库 urllib）
      narrate(path, provider=auto)  provider=auto 且环境变量齐备才走 LLM，失败降级 offline

环境变量：SPXH_LLM_BASE_URL / SPXH_LLM_API_KEY / SPXH_LLM_MODEL。
接口：GET /api/narrate?path=...&provider=auto|offline&max_tokens=800；前端新增「报告」页
（mode 徽标 / headline / confidence / 逐条证据表 / uncertainties / next_actions / 提示词折叠 / 重新生成）。

### 4.3 实测

离线模式（本机未配 key，按设计降级）：

- mode=offline，model=offline-rule-based，confidence 0.77；
- headline：「QPSK，Es/N0 约 9.8 dB，符号速率 1000.0 Hz，帧同步锁定（6/6 帧 CRC 通过）」；
- sections：signal(6 条证据) / modulation(3) / frame(6) / cyclostationary(3)；
- 确定性：同一输入两次调用 sections 完全一致（有单测）。

### 4.4 下一步可以怎么加深

1. **工具调用代理**：把 analyze/classify/demod/frame/ssca 暴露成工具，让模型自己决定"先看谱相关还是先解帧"，
   多轮迭代到证据自洽 —— 这才是真正的"分析代理"，而不是一次性总结。
2. **LLM 做参数建议**：把已知的失败模式（低置信度、CRC 全灭、门控 fallback）作为上下文，
   让模型给出"下一步该调什么"（换案例 / 开盲恢复 / 标擦除 / 重训分类器），并与平台动作闭环。
3. **LLM 做异常解释**：把 M1~M8 的矛盾（例如谱相关给出 1000 Hz 而 M1 给出 1200 Hz）交给模型解释可能原因。
4. **LLM 生成验收/交付文档**：它已经把整条链路的证据结构化，写报告是它的强项，
   数值仍然由管线提供 —— 这正是本模块的边界。

## 5. 本轮未做

- **跨帧积累 / 更长前导**：需要动帧结构（前导重复计数字段）或同步器，留到下一轮；
  目前 5~8 dB 的召回瓶颈已经定位到"帧头保护"（本轮已解决一部分）与"前段瞬态"（未解决）。
- **LLM 端到端真调用**：本机没有 key，只验证了离线路径与降级路径；真实 key 的联调留待有凭据的环境。
- 联合译码（M8 的误差+擦除）**接入端到端曲线**尚未做，仍只在码字级验证。

## 5.1 事故与修复：工作台因为"客户端中途断开"整体退出

**现象**：工作台进程在运行一段时间后自行退出（exit 1），日志里是成片的
`ConnectionResetError [WinError 10054]` traceback，端口不再监听 —— 界面直接打不开。

**根因**：浏览器刷新/关标签页会让"正在写的 HTTP 响应"瞬间失去对端。原先的实现里：

1. 处理线程抛出的连接异常会被 `handle_error` 打成**完整 traceback**（几十行一条），60 次断开就能刷满日志，
   日志管道被打爆会反过来影响进程；
2. `_send_json` / `_send_file` 里 `self.wfile.write` **没有保护**，对端已断时抛异常 →
   被外层 `except Exception` 捕获 → 先 `traceback.print_exc()` 再回 500（再次写死 socket）→ **又一次异常**，
   于是每断开一次就产生两个 traceback（实测 40 次断开 = 10 个 traceback + 若干 500）。

**修复**（都在 spxh/web/server.py）：

- `SPXHHTTPServer`：专门忽略 ConnectionReset/Aborted/BrokenPipe/Timeout —— 只记一行"累计忽略 N 次"；
- `_safe_write()`：写响应失败时安静收场（置 `close_connection`），不再抛；
- 响应头阶段也加了同样的保护；客户端提前断开走单独的 except 分支，不再打 traceback；
- `traceback.print_exc()` 自身也包了保护（stderr 可能已经断了）；
- **外层兜底循环**：`serve_forever` 万一还是退出，1 秒后继续服务，不整体不可用；
- 端口被占用时给出明确中文提示并以 exit 2 退出，而不是抛栈。

**验证**：60 次"发一半就断开"的请求打过去 —— 服务仍返回 200，日志 **0 个 traceback、0 个 500**（修复前同样的
压力是 10 个 traceback + 多个 500）。回归测试 `tests/test_server.py`（4 项）覆盖：服务类属性、
`handle_error` 吞掉连接类异常、真实断开压测后服务仍可用。

**第二次"无声退出"的真正原因（关键教训）**：连接问题修完之后，工作台仍然会隔一段时间自己消失，
而且**日志末尾没有任何异常**。同时 `python -m pytest -q` 也开始"跑到 84% 就断"。
把 pytest 的输出**重定向到文件**后再跑：**exit 0，全部通过** —— 说明测试本身没问题，
是"往被捕获的 stdout 管道里写大量输出"这件事让进程被打断。

工作台同理：逐请求日志默认打在 stdout，浏览器一刷新就是十几行，管道被写爆 → 进程被杀。
**修复**：逐请求日志默认写文件（`--log models/web.log`，超过 2 MB 自动截断），
stdout 只留一行启动横幅；前台调试想看得见就用 `--verbose`。
再加上一个**监督循环**（进程退出 2 秒后自动拉起），并做了真实验证：

    Stop-Process -Id <服务进程> -Force   # 杀掉
    12 秒后 /api/health -> 200           # 监督进程已经把它拉回来
    [supervisor] serve exited at ..., restarting in 2s

修复后实测：连续 60 个真实请求（含 frame/ssca/narrate 重接口）**60/60 成功**，
stdout 总共 111 字节，**0 次重启**。
