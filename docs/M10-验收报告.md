## 2. 配置模型：为什么不是"只读环境变量"

在桌面环境里让使用者去改系统环境变量、再重启终端，体验很差；把密钥写进代码或前端则绝对不能接受。
折中方案是**服务端本地文件 + 脱敏回显 + 只提交改动字段**：

优先级：**本地文件 models/llm_config.json > 环境变量（SPXH_LLM_*） > 内置默认**，
并且**每一项都回报来源**（file / env / default / override），前端逐项标注 ——
"这个模型名到底哪来的"是可解释性的一部分。

安全约定（都有测试覆盖）：
- 密钥只落本地文件；接口只回显 `api_key_hint`（尾 4 位，如 `****abcd`）；
- **明文绝不出现在任何接口响应里**（测试直接断言 `"sk-secret" not in json.dumps(masked)`）；
- 不写日志；前端输入框用 password 类型；
- 提交空 `api_key` 视为"不改动"（避免前端没改密钥却把它覆盖掉），要删必须显式 `clear_api_key=true`；
- 保存是**原子**的（临时文件 + `os.replace`），失败不破坏原文件。

字段校验（非法值返回 400 + 中文原因）：`base_url` 必须 http(s)://、`temperature` 0~2、
`max_tokens` 1~32000、`timeout_s` 1~600、`model` 非空、未知字段直接拒绝。

## 3. 接口（契约 §17）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /api/llm/config | 脱敏配置 + 来源 + ready + 环境变量"是否设置" |
| POST | /api/llm/config | 只提交要改的字段；返回同样的脱敏结构 |
| POST | /api/llm/test | 真发一次最小请求：ok/latency/reply/models/中文错误（失败也 200） |
| GET | /api/llm/models | 拉取模型列表（失败返回 error 文案） |

`/api/narrate` 的行为随之明确：`provider=auto` 只有 **enabled 且有 key** 才走 LLM，
`provider=llm` 强制（未配置则降级 + warnings），`offline` 永远离线；
走 LLM 时响应带脱敏的 `llm` 块（base_url / model / api_key_hint）。

## 4. 实测证据（都是本机真实跑出来的）

**核心逻辑（tests/test_llm_config.py，20 项）**：用一个**离线假 LLM 服务**（stdlib http.server 模拟
OpenAI 的 /models 与 /chat/completions）覆盖：默认值、保存与脱敏、空 key 不覆盖、显式清 key、
9 种非法值被拦、env 生效、file 覆盖 env、override 临时生效且不落盘、模型列表、
连通性成功（reply=ok、latency）、错误 key 给中文原因、无 key 给明确原因、
narrate 在 auto/offline/enabled=false 三种情况下的走向。

**真机接口（服务进程实测）**：

    GET  /api/llm/config                 -> 200 ready=false base=默认 hint=null source=default
    POST /api/llm/config (base/key/model)-> 200 hint=****9876 ready=true source=file，明文泄漏=false
    POST /api/llm/test                   -> 200 ok=false "连接失败：[WinError 10061] ..."
    POST /api/llm/config (temperature=9) -> 400 "temperature 必须在 0 ~ 2 之间"
    GET  /api/llm/models                 -> 200 error="连接失败..." models=[]
    POST /api/llm/config (还原+清 key)   -> 200 ready=false hint=null
    GET  /api/narrate                    -> 200 mode=offline

**命令行**：`python -m spxh llm` 打印配置表（含每项来源与配置文件路径）；
`--set model=qwen2.5:7b --test --models` 一步设置并自检。

## 5. 数值落地检查（把"不许编数"变成可回归的硬约束）

LLM 最危险的失败不是文笔，而是**编造一个看起来很专业的数字**。提示词里写"只许引用给定字段"
只是祈使句；M10 把它变成可自动检查的判据：

- `collect_evidence_numbers(evidence)`：证据表里出现过的所有数字（含 confidence、嵌套列表）作为白名单；
- `check_numeric_grounding(report, evidence)`：抽取报告正文里的**独立数字**（不能紧贴字母，
  否则 Es/N0 的 0、16QAM/2FSK 里的数字会形成大量假警报 —— 这是第一版踩的坑），
  逐个在白名单里查（带 1% 容差），不匹配的进 `unsupported`；
- 结果写进报告 `grounding`，不落地就追加 warning，前端可见。

实测：**离线报告 26 个数字全部可溯源**（`grounded: true`）—— 这也顺带给渲染器做了自证；
造一个"编数"的假 LLM 输出（"Es/N0 约 12.5 dB、符号速率 1234.5 Hz" 而证据里只有 9.76）会被准确标出这两个数字。

## 8. 附：本轮修掉的三个接口细节（前端 teammate 联调发现）

1. **空 body 的 POST 会把默认配置物化落盘**（source 从 default 变 file）—— 探测式请求不该改变来源；
   现在空 body / 空字段一律 **no-op**（有单测）。
2. config_path 回**相对路径**（另给 config_path_abs），界面上更好读。
3. /api/llm/models 的错误压成**单行短理由**（服务商返回的多行 JSON 不再糊满界面）。


## 9. DeepSeek 配置报错：定位与修复（用户反馈驱动）

**现象**：用户配置 DeepSeek 后报错，且**配置文件没有落盘**（服务端仍是默认值）——
说明配置没保存成功，或只做了"不落盘的测试"。

**定位**：DeepSeek 是 OpenAI 兼容协议，但有四个常见的坑，平台侧都做了处理：

| 坑 | 现象 | 现在的行为 |
|---|---|---|
| 把**完整接口地址**粘进 Base URL（`.../chat/completions`） | 拼接后变成 `.../chat/completions/chat/completions` → 404 | **自动归一化**：去掉末尾 /chat/completions、/completions、/models 与多余斜杠；保存后用响应值回填表单 |
| 模型名写错（如 `deepseek-v3`、`deepseek-coder`） | 400 Model Not Exist | 错误文案带原因 + `hint` 列出该服务商**可用模型清单**（DeepSeek 是 deepseek-chat / deepseek-reasoner） |
| **`deepseek-reasoner` 不支持 JSON 模式** | 400 response_format is not supported | 平台**自动去掉 response_format 重试一次**（实测：reasoner 下报告链路仍然走通，mode=llm） |
| 余额不足 / 密钥无效 / 限流 | 402 / 401 / 429 | 分别给出中文原因（402 余额不足、401 密钥无效或未授权、429 被限流） |

**同时补上诊断能力**：`POST /api/llm/test` 会回 `checked.chat_url`（**实际请求地址**）与
`hint`（可操作提示）——"报错到底为什么"有了答案；`GET /api/llm/config` 增加 `presets`
（DeepSeek / OpenAI / 本地 Ollama / 自定义，前端一键填充）。

**真机验证**（用一个"像 DeepSeek 一样拒绝 JSON 模式、并且严格校验路径"的假服务跑完整链路）：

    ① POST /api/llm/config（故意粘 .../v1/chat/completions） -> 归一化后 base_url=.../v1，ready=true
    ② POST /api/llm/test                                    -> ok=true，实际请求地址 .../v1/chat/completions，模型表 [deepseek-chat, deepseek-reasoner]
    ③ GET  /api/narrate（模型用 deepseek-reasoner）          -> mode=llm（自动降级重试生效），llm 块脱敏 ****0001
    ④ 地址写错 -> 404：中文提示"检查 Base URL 是否多写了 /chat/completions"
    ⑥ 模型名写错 -> hint="该服务商可用模型：deepseek-chat、deepseek-reasoner"

**正确的 DeepSeek 配法**（任选其一）：

    Base URL: https://api.deepseek.com     （写 https://api.deepseek.com/v1 也可以）
    模型:     deepseek-chat（对话） / deepseek-reasoner（推理，平台会自动处理 JSON 模式差异）
    API Key:  sk- 开头，从 platform.deepseek.com 获取

    # 或命令行一步到位
    python -m spxh llm --set base_url=https://api.deepseek.com --set model=deepseek-chat --set api_key=sk-xxx --test
    python -m spxh llm --test --models

**如果还报错**：把 `POST /api/llm/test` 返回里的 `error` 与 `checked.chat_url` 一起发我——
前者是服务商的原话，后者说明请求到底打到哪个地址，两者一对照就能定位。
