## 2. 低信噪比帧召回：软前导判决

**诊断**：帧召回损失的来源不是相关峰不够高，而是**解析阶段要求 13 位 Barker 全对**。
BER 2%~5% 时单帧通过率只有 50%~75%，整帧被丢掉。

**改法**：有 LLR 时改用软判决 —— 最多容忍 2 位不符 **且** 软相关为正
（LLR 约定：正 => 更可能是 0；期望位映射成 ±1 后求和）。误判由**帧头 CRC-8 与帧 CRC-16 两级**兜底，
所以这不是放宽判据，而是换成更充分利用信息量的判据。

实测（16 帧，QPSK，0.35 符号偏移 + 37 Hz 频偏，盲恢复开启）：

| Es/N0 | 编码 | 硬前导 解析/CRC | 软前导 解析/CRC | 召回提升 |
|---|---|---|---|---|
| 5 dB | conv | 0/0 | **3/2** | +3 |
| 6 dB | conv | 4/4 | **10/10** | **+6** |
| 8 dB | ccsds | 12/10 | **14/11** | +2 |
| 10 dB | conv | 13/13 | **16/16** | +3 |
| 各处 | none（无编码） | 基本不变 | 基本不变 | 0 ~ +1 |

无编码链路几乎不变是**预期**的：它们没有冗余，失败原因是载荷 CRC 不过，而不是前导读不出来 ——
如实记录，不粉饰。

## 3. 跨帧积累：实测失败并删除

原计划是"估计帧周期 -> 沿 k + jP 做非相干积累（约 sqrt(M) 增益）"。实测两种周期估计器都不可靠：

- **对 |相关| 做自相关**：QPSK 的 |相关| 基线并不贴近 0（随机数据经常凑出相关值），真周期峰被淹没；
  且整数周期搜索会因帧周期是小数（581 比特 / 2 = 290.5 符号）而漂移。
- **对显著峰的两两间隔做直方图**：被噪声峰污染，估出 22 / 188 / 2385 这类值（真值 581 / 290.5 / 1192.5）。

结论：没有额外先验时，帧周期估计本身就是一个不比帧检测简单的问题。该模块**已删除**
（不留没有实测收益的机制），力气放在直接有效的软前导上。将来若做，正确形态是
"用已知帧长假设构造梳状假设"，而不是盲估周期。

## 4. 联合译码接进链路：机制可用，但**默认策略要克制**

链路侧接线：parse_frame(..., erasure_decoding=True) -> decode_payload(..., erasure_from_llr=True)
-> 由软信息自动给出擦除位置 -> RS 误差 + 擦除联合译码（2f + e <= 2t）。

**实测发现（重要）**：最初的"|LLR| 均值低于门限就标擦除"在纯 AWGN 下**反而变差**：
90% CRC 门限从 8.78 dB 升到 9.20 dB，8 dB 处通过率 0.77 -> 0.31。
原因是 AWGN 下低 |LLR| 的符号**大多是正确**的，而每个错误擦除要吃掉半个纠错能力。

**改法**：只把**连续成段**的弱区（>=3 个符号）标为擦除 —— 突发是连续的，AWGN 的低置信度是零散的。

| 场景 | 结果 |
|---|---|
| AWGN 门限曲线（7~12 dB） | 与不标擦除**逐点相同**（+0.000），门限都是 8.78 dB —— 不退化就是目标 |
| 8 dB 全链路自动擦除数量 | **0 个**（不虚标） |
| 已知位置突发（M7-C，RS(76,60)） | 9/12/16 字节突发：不标擦除失败、标了擦除**全部通过**；17 字节（> 2t）如实报不可纠 |

一句话：**擦除信息值钱的是"位置可信"，不是"置信度低"**。这条已写进代码注释与本文档。

## 9. 突发检测 + 自动擦除的端到端验证（M12-C）

### 9.1 做了什么

| 环节 | 实现 | 位置 |
|---|---|---|
| **信号侧突发检测** | 滑动 RMS（2 符号窗）+ 双判据（**深度 < -12 dB** 且 **低于中位数 - 4×MAD**）+ 边缘抑制 + 最小长度 1.5 符号；输出区间 / 深度 / 置信度 | `spxh/core/dsp/burst.py` |
| 两类损伤 | **collapse**（遮挡、置零、深衰落：功率塌陷）与 **jam**（压制、强干扰：功率抬升 +6 dB 以上） | 同上 |
| 信号 → 符号 | 定时环现在暴露**每个判决符号的采样位置** `DemodResult.symbol_samples`（原本只内部使用） | `spxh/core/demod/{sync,receiver}.py` |
| 符号 → 码字 | `extract_frames(auto_erasures=True)`：突发区间 → 符号区间 → 帧内比特 → 8 比特 RS 符号下标，只保留落在编码段内的位置 | `spxh/core/framesync/extract.py` |
| **预算仲裁** | 候选擦除预算 [0, 实测个数, 16, 8, 4, 2] 逐个尝试，**CRC 说了算**；预算里含 0 | `spxh/core/framing/format.py` |

**为什么要有"预算仲裁"这一步（本轮最有价值的工程结论）**：检测区间比真实损伤宽（滑动窗边界 + 符号取整），
实测 20 符号的突发会标出 **31~33 个**擦除位置，而 RS(78,62) 的容量是 **2t = 16** ——
擦除数一旦超过它，译码器直接判不可纠。第一版实现下 9 dB 场景从 6/8 掉到 **4/8**（越帮越忙）。
现在改成"候选预算含 0、CRC 仲裁"，**自动擦除在最坏情况下只能退回普通译码，永不更差**。

### 9.2 实测（20 符号突发打在载荷编码段中央，QPSK，8 帧）

| 场景 | 不开擦除 CRC | 自动擦除 CRC | 检测 | 结论 |
|---|---|---|---|---|
| 干净信号（20 dB） | 8/8 | 8/8 | 0 段 ✓ | 不虚报、不退化 |
| 遮挡式置零（collapse） | 8/8 | 8/8 | 1 段 ✓ | **置零对 QPSK 是弱损伤**：零点落到固定判决点，20 符号里约 8 个真出错，仍在 t=8 内 |
| 压制 factor 1.5 / 2 / 3 / 5（jam） | 8/8 | 8/8 | 各 1 段 ✓ | 检出正常，但同样落在 RS 余量内 |
| 压制 factor 10（jam） | **0 帧** | 0 帧 | 1 段 ✓ | 干扰强到**连帧同步/环路一起打掉**，整段记录失锁 |
| 低信噪比窗口：9 dB × factor 2 | 6/8 | 6/8 | 1 段 ✓ | 无增益（且不再是 -2） |
| 9 dB × factor 4 / 10 dB × 2 / 10 dB × 4 | 7、5、7 / 8 | 7、5、7 / 8 | ✓ | 逐点相同 |
| 11 dB × factor 2 / 4 | 8/8 | 8/8 | ✓ | 逐点相同 |
| **打中帧头** 16 符号 | 7/7（那一帧直接消失） | 7/7 | ✓ | 帧头不编码：解析都过不了，擦除无从下手 |

### 9.3 诚实结论

1. **检测器可用**：塌陷与压制两类都能自动检出，干净信号与纯噪声**零假报**，位置/深度/置信度经过校验；
2. **链路已打通**：检测 → 符号 → 码字 → 联合译码全程自动，且**永不帮倒忙**（11/11 场景不退化）；
3. **但本配置下没有帧级增益** —— 原因不是擦除机制，而是**同步环**：
   局部突发要么落在 RS 的 t=8 余量内（本来就能过），要么强到把同步一起打掉（损伤扩散到整帧，远超 2t）；
4. 因此下一步不该继续加擦除，而是**同步侧抗突发**：突发期间冻结/预测定时与载波环（或先做置零修复再解调），
   让损伤重新"局部化"，擦除译码才有用武之地。这条已写进路线图。
5. 另外一个反直觉但值得记的现象：**遮挡式置零对 QPSK 是很弱的损伤**（零点会落到某个固定判决点上），
   用它做"突发实验"会得到"系统很鲁棒"的假象 —— 报告里如实保留了这组对照。

## 10. 同步侧抗突发：置零 + 环路冻结（M13 尝试，结论为"不添乱但无增益"）

### 10.1 做了什么

针对 §9 的结论（"瓶颈在同步环"），本轮把抗突发做进解调器：

| 环节 | 实现 |
|---|---|
| **突发置零（blanking）** | 检测到的区间先把采样置零（两端 0.5 符号线性过渡），不让强干扰的能量经匹配滤波与 AGC 污染环路 |
| **定时环冻结（coast）** | `TimingRecovery.run(..., freeze_regions=...)`：采样位置落在突发区间内时**不更新** `mu`/`integrator`，按当前状态滑行 |
| **载波环冻结** | `CarrierRecovery.run(..., freeze_mask=...)`：突发符号上只按当前相位/频率旋转，**不更新**相位与频率；这些符号的相位误差记为 0（明确表示"这段不可信"） |
| **接线** | `extract_frames(auto_erasures=True)`：检测提前到**解调之前**，区间同时用于置零/冻结与擦除映射；证据表记录 `blanked_samples` / `frozen_symbols` |

### 10.2 实测（载荷段 20 符号干扰，8 帧，20 dB）

| factor | 全关 | 仅同步抗突发 | 同步抗突发 + 自动擦除 |
|---|---|---|---|
| 3 | 8/8 | 8/8 | 8/8 |
| 6 | 0/2 | 0/1 | 0/1 |
| 10 | 0/0 | 0/0 | 0/0 |

**结论：没有帧级增益。** 机制确实生效了（实测每次置零约 190 采样、冻结约 24 个符号），
但强干扰下记录仍然整体失锁。

### 10.3 根因（有数据支撑）

1. **匹配滤波把洞展宽**：RRC 跨度 16 符号，一个 20 符号的洞经匹配滤波后有效损伤约 **36 个符号**，
   而 RS(78,62) 的擦除/纠错总预算只有 **2t = 16** —— 无论同步怎么冻结，擦除都装不下；
2. **强干扰会打掉帧同步本身**：factor ≥ 6 时整个记录只剩 0~2 帧能被解析，
   这是**前导相关**层面的失效，不是译码层面的；
3. 因此"给定码率的突发容量"才是硬约束：**有效损伤（含滤波展宽）必须 ≲ 2t 才有擦除的用武之地**。

### 10.4 一个方法论教训（已写进判据）

第一版判据拿"抗突发 + 擦除"去比"全关"，得出"擦除可能更差"的错误结论 —— 其实两者**解调路径不同**
（一个置零+冻结，一个没有），不可混比。现在判据改成**同口径**：同一解调路径下"标擦除 vs 不标擦除"，
并保留"抗突发不得让结果变差"的独立判据。两条都 PASS。

### 10.5 未完成 / 下一步

- **交织在信号级没有复现出增益**：M6-C 已在**比特级**证明交织对突发有效（32 比特突发 0/8 → 8/8），
  但本轮在**信号级** 20 符号干扰下（干扰位置相对帧结构随机）没有复现出来，而且交织布局在高干扰下
  出现了整段解析失败 → 如实记为**未完成项**，需要专门排查"交织 × 帧同步"的相互作用；
- **真正该做的方向**：既然硬约束是"有效损伤 ≤ 2t"，那么出路是
  ① **更强的码**（更低的码率，换更大的 t）；② **跨码字交织 + 符号级去交织**（把 36 符号的有效损伤
  打散到 5 个 RS 码字上，每码字只承担 ~7 个错误，正好在 t=8 之内）；③ **把洞"删掉"而不是"标擦除"**
  （帧结构上支持可变长度载荷）。
  ②是最有希望的一条，且我们已有交织器与 CCSDS 符号交织——下一步优先做它。
